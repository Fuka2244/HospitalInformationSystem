# Hospital Information System 项目面试题库

> 适用方向：Java 后端、Java 全栈、AI 应用开发实习/校招
> 项目技术栈：Java 21、Spring Boot 3.2.5、MyBatis-Plus、MySQL、Redis、Kafka、JWT、LangChain4j、Vue 3、TypeScript

## 一、面试前先记住的项目主线

这个项目不是简单的医院 CRUD，而是围绕“患者预约—医生接诊—生成病历和处方—药师审核发药—患者缴费—生成医疗报告”形成完整业务闭环。

最值得重点准备的三条技术主线：

1. 高并发预约：Redis 分布式锁、Lua 原子预扣库存、MySQL 条件更新与乐观锁。
2. 医疗业务事务：就诊结束后同时生成病历、处方、处方明细和费用；发药时扣库存并记录流水。
3. AI 医疗助手：LangChain4j 接入模型，药品字段级分块，向量检索与关键词检索通过 RRF 融合，Kafka 承接异步 AI 任务。

### 1 分钟项目介绍参考

我做的是一个前后端分离的医院信息系统，服务患者、医生、药师和管理员四类角色。后端使用 Spring Boot、MyBatis-Plus 和 MySQL，前端使用 Vue 3 和 TypeScript。核心业务包括预约挂号、医生接诊、电子病历、处方审核、药品库存、费用支付和 AI 医疗报告。

这个项目中我重点解决了三个问题。第一是热门号源的并发预约，通过 Redis 分布式锁、Lua 原子扣减和 MySQL 乐观锁避免超卖；第二是就诊和发药业务的一致性，使用事务维护病历、处方、账单、库存和库存流水；第三是 AI 药品检索，使用 LangChain4j 将药品按功效、成分、禁忌等字段切分，通过向量与关键词混合检索召回候选药品，再交给大模型生成结构化建议。系统还通过 JWT 和 Redis 管理登录会话，通过 Kafka 处理耗时 AI 请求。

### 3 分钟项目介绍的展开顺序

1. 业务背景：多角色协作的门诊闭环。
2. 系统架构：Vue 前端、Spring Boot 分层后端、MySQL 持久化、Redis 缓存和并发控制、Kafka 异步解耦、LangChain4j AI 接入。
3. 最难问题：预约防超卖、跨表事务、药品混合检索。
4. 测试验证：单元测试、集成测试、并发测试、缓存性能测试、Selenium 端到端测试、检索指标评测。
5. 复盘改进：事务代理、自建 Redis 锁续期、双写一致性、库存幂等仍可继续加强。

## 二、项目与架构题

### 1. 这个项目解决了什么问题？

**参考回答：**

项目将患者、医生、药师和管理员的工作串成一条完整门诊流程。患者完成预约和缴费，医生接诊并生成病历与处方，药师审核处方并发药，管理员管理排班和统计数据。它解决的不只是信息展示问题，还涉及号源竞争、状态流转、费用生成、库存一致性和医疗数据权限。

**追问：为什么不能只做成几个独立 CRUD 模块？**

因为预约、就诊、处方、费用和库存之间存在强业务约束。例如只有接诊完成后才能生成病历，只有审核通过的处方才能发药，发药必须同时扣减库存并记录流水。这些约束需要事务、状态机和权限控制，而不是孤立表操作。

### 2. 系统整体架构是什么？

**参考回答：**

系统采用前后端分离架构：

- Vue 3 前端通过 Axios 调用 REST API，Pinia 管理登录和业务状态，Vue Router 负责页面路由。
- Spring Boot 后端按 Controller、Service、Mapper、Entity/DTO 分层。
- MySQL 保存核心业务数据。
- Redis 用于缓存、JWT 会话、分布式锁和号源库存。
- Kafka 用于异步 AI 任务。
- LangChain4j 封装对话模型和 Embedding 模型。
- iText 负责医疗报告 PDF 导出。

### 3. 为什么选择 Spring Boot + MyBatis-Plus？

**参考回答：**

Spring Boot 适合快速搭建 REST 服务，并且对 Redis、Kafka、事务和参数校验都有成熟集成。MyBatis-Plus 可以减少普通单表 CRUD 代码，同时仍允许在 Mapper 中编写预约号源条件更新、乐观锁更新等定制 SQL。相比完全依赖 ORM，它更便于控制关键 SQL。

### 4. 项目中 DTO、Entity 和 VO 为什么要分开？

**参考回答：**

Entity 对应数据库结构，DTO 表示接口输入，VO 或响应 DTO 表示对外输出。分开后可以：

- 防止把密码、内部状态等字段直接暴露给前端。
- 对不同接口设置不同参数校验。
- 避免数据库字段变化直接破坏 API。
- 支持把医生名、科室名等多表信息组合后返回。

### 5. 统一响应 `Result` 有什么价值？

**参考回答：**

统一响应可以固定成功标志、错误码、提示信息、数据、总数、请求路径和 traceId 等字段，前端只需要一套拦截处理逻辑。与全局异常处理器结合后，业务异常、参数异常和系统异常能够使用一致格式返回。

**追问：HTTP 状态码和业务错误码是否还需要同时使用？**

需要。HTTP 状态码表达协议层结果，如 401、403、404、500；业务错误码表达更细的领域错误，如“号源已满”“处方未审核”。不应永远返回 HTTP 200 再只看业务码。

### 6. 系统的核心领域对象有哪些？

**参考回答：**

- 患者、医生、药师、管理员：参与业务的角色。
- 科室、医生排班、预约：预约挂号领域。
- 就诊记录、病历、处方、处方明细、处方审核：诊疗领域。
- 药品、药品库存、库存流水：药房领域。
- 账单：费用领域。
- 医疗报告、聊天历史：报告与 AI 交互领域。

### 7. 从预约到发药的完整流程是什么？

**参考回答：**

患者选择科室、医生和排班后创建预约，系统占用号源并生成挂号费；登记后医生叫号、开始接诊并填写诊断；结束接诊时生成病历，如果医生开药则生成处方、处方明细和药品费用；药师审核处方，通过后才能发药；发药时检查并扣减库存、写库存流水，最后更新处方状态。

### 8. 项目中哪些场景必须使用事务？

**参考回答：**

- 创建预约与生成挂号账单。
- 取消预约、释放号源与取消相关账单。
- 结束就诊时更新预约、就诊记录，并生成病历、处方、处方明细和费用。
- 药师审核处方并写审核记录。
- 发药时扣减多个药品库存、写流水并更新处方状态。
- 支付多笔费用时批量更新账单状态。

原则是一个业务动作涉及多个必须同时成功或同时失败的数据库写操作时，应放在同一事务边界。

## 三、高并发预约与 Redis 题

### 9. 如何避免同一排班号源被超卖？

**参考回答：**

项目有两套实现：

1. Redis 分布式锁：按“医生 ID + 日期 + 时段”生成锁 Key。拿到锁后执行 MySQL 条件更新，只有 `booked_count < max_patients` 时才递增。
2. Redis 预扣库存 + MySQL 乐观锁：先用 Lua 脚本原子扣减 Redis 号源，再按 `version` 条件更新 MySQL；冲突时最多重试 3 次，失败则回补 Redis。

MySQL 条件更新是最终防线，即使应用层并发判断失效，也不会把预约数更新到容量上限以上。

### 10. 为什么不能先查询剩余号源，再执行普通更新？

**参考回答：**

“查询后更新”不是原子操作。两个请求可能同时读到剩余 1 个号源，然后都完成更新，导致超卖。应将判断和更新写进同一条 SQL：

```sql
UPDATE doctor_schedule
SET booked_count = booked_count + 1
WHERE doctor_id = ?
  AND schedule_date = ?
  AND time_slot = ?
  AND booked_count < max_patients
  AND status = 1;
```

根据影响行数判断预约是否成功。

### 11. Redis 分布式锁是怎么实现的？

**参考回答：**

加锁使用带过期时间的 `SETNX`，锁值使用 UUID，避免不同线程误删彼此的锁。释放锁时使用 Lua 脚本原子完成“比较锁值”和“删除 Key”：

```lua
if redis.call('get', KEYS[1]) == ARGV[1] then
    return redis.call('del', KEYS[1])
else
    return 0
end
```

过期时间用于防止持锁进程崩溃后形成死锁。

### 12. 为什么解锁一定要使用 Lua 脚本？

**参考回答：**

如果先 `GET` 判断锁值，再单独 `DEL`，两条命令之间锁可能刚好过期并被其他线程重新获得，此时旧线程会误删新线程的锁。Lua 在 Redis 内部原子执行比较与删除，可以避免这个竞态条件。

### 13. 当前自建分布式锁还有什么问题？

**参考回答：**

当前锁默认 10 秒过期，没有自动续期。如果业务执行超过 10 秒，锁会提前失效，另一个请求可能进入临界区。进一步可以：

- 使用 Redisson 的 watchdog 自动续期。
- 合理估算锁超时并监控业务耗时。
- 让数据库条件更新继续承担最终一致性保护。
- 对关键操作增加幂等约束。

### 14. Redis 号源预扣为什么使用 Lua？

**参考回答：**

库存判断和扣减必须原子完成。Lua 先读取库存，库存不存在返回未初始化，库存小于等于 0 返回失败，否则执行 `DECR`。如果在 Java 中分别执行 GET 和 DECR，同样会出现多个线程都判断有库存的竞态。

### 15. Redis 与 MySQL 的号源数据如何保持一致？

**参考回答：**

当前实现以 MySQL 为最终事实来源，Redis 用于快速拦截无库存请求：

1. Redis 先预扣。
2. MySQL 使用版本号进行条件更新。
3. MySQL 更新失败或异常时回补 Redis。
4. 系统提供从数据库同步号源到 Redis 的能力。

这属于补偿式最终一致性。生产级方案还需要定时对账、重试任务、操作日志或消息驱动补偿，处理进程在“数据库成功但响应前崩溃”等极端情况。

### 16. Redis 库存初始化有没有并发风险？

**参考回答：**

有。当前流程先判断初始化标记，不存在时从 MySQL 查询并写入 Redis。多个请求可能同时发现“未初始化”，后写入的请求有机会覆盖其他请求已经预扣后的值。可以用初始化锁，或者用一个 Lua 脚本/`SETNX` 原子完成首次初始化，避免覆盖已存在库存。

### 17. 乐观锁和分布式锁有什么区别？

**参考回答：**

- 分布式锁在进入临界区前进行互斥，适合冲突较高、同一资源只能串行修改的场景。
- 乐观锁允许并发执行，在提交更新时通过版本号检测冲突，适合冲突相对可控的场景。
- 项目中 Redis 负责快速预扣和流量削峰，MySQL 版本号负责最终写入校验。

### 18. 如果乐观锁冲突，为什么要限制重试次数？

**参考回答：**

无限重试会在热点号源上放大数据库压力，甚至形成活锁。项目限制为 3 次，失败后回补 Redis 库存并让客户端稍后重试。生产中还可加入随机退避，降低大量请求同时重试造成的冲击。

### 19. 取消预约时需要处理哪些一致性问题？

**参考回答：**

需要同时：

- 校验预约属于当前患者且状态允许取消。
- 更新预约状态和取消原因。
- 取消或退款相关挂号账单。
- 减少 MySQL 已预约数量。
- 回补 Redis 号源库存。
- 清理相关缓存。

这些步骤必须防止重复取消，否则可能重复回补号源。可以用状态条件更新保证幂等，例如只允许从“已预约”原子更新到“已取消”。

### 20. 如何验证预约真的没有超卖？

**参考回答：**

项目提供了分布式锁并发测试，包括 100 个线程争抢同一锁、同一排班并发预约以及不同 Key 并行执行。更完整的验证应检查：

- 成功预约数不超过最大号源数。
- `booked_count` 等于有效预约记录数。
- Redis 剩余库存加成功预约数等于初始库存。
- 失败、超时、取消和服务重启后仍能对账。
- 多实例而不只是单 JVM 下的并发结果。

## 四、事务、处方、库存与支付题

### 21. `@Transactional` 的实现原理是什么？

**参考回答：**

Spring 通常通过 AOP 代理拦截被代理对象的公开方法，在调用前开启事务，正常结束时提交，抛出符合回滚规则的异常时回滚。事务上下文通常绑定到当前线程。

### 22. 项目中的事务自调用有什么隐患？

**参考回答：**

`createAppointment()` 在同一个类内部调用带 `@Transactional` 的 `doCreateAppointment()`。这种 `this` 内部调用不会经过 Spring 代理，因此后者的事务注解可能不生效。结果是号源递增、预约插入和账单插入不能保证处于同一事务。

改进方式：

- 把事务放到外部实际被调用的 `createAppointment()`。
- 或将事务方法拆到另一个 Service，通过代理调用。
- 或使用 `TransactionTemplate` 明确控制事务边界。

这是面试时应主动承认并给出修复方案的真实代码问题。

### 23. 为什么 `@Transactional` 不能保证 Redis 与 MySQL 一起回滚？

**参考回答：**

普通 Spring 数据库事务只管理同一个关系型数据库事务资源，Redis 操作和 Kafka 消息通常不在这个本地事务中。MySQL 回滚不会自动回滚 Redis 预扣。因此需要补偿、对账、事务消息、Outbox 或 Saga 等最终一致性方案。

### 24. 结束就诊时会产生哪些数据？

**参考回答：**

系统先把预约更新为已完成，并记录就诊结束时间、诊断、治疗和备注；然后创建电子病历。如果有处方明细，则创建处方、逐条创建处方项，根据药品单价和数量生成药品账单，并额外生成取药服务费。

### 25. 为什么使用 `BigDecimal` 计算费用？

**参考回答：**

`double` 使用二进制浮点表示，计算十进制金额可能产生精度误差。`BigDecimal` 可以精确表示十进制金额，适合医疗费用、药品价格等场景。数据库应配合 `DECIMAL` 字段，并明确舍入规则。

### 26. 发药为什么要先检查全部库存，再统一扣减？

**参考回答：**

先检查全部处方项可以尽早发现任一药品不足，避免业务上出现只发出部分药品的结果。后续所有扣减和流水写入放在同一事务中，任何一步抛出异常时数据库操作一起回滚。

### 27. 当前发药逻辑在并发下有什么风险？

**参考回答：**

当前是“查询库存—Java 判断—更新库存”，两个药师并发操作时可能都看到库存充足，造成丢失更新或重复发药。事务本身并不能自动避免这种竞态。

可改为：

- 条件更新：`UPDATE ... SET quantity = quantity - ? WHERE id = ? AND quantity >= ?`。
- 或查询时使用行锁 `SELECT ... FOR UPDATE`。
- 给处方状态做条件更新，只有“审核通过”才能原子迁移到“已发药”。
- 增加发药幂等键或唯一业务约束。
- 对多药品按固定顺序加锁，降低死锁风险。

### 28. 库存流水为什么重要？

**参考回答：**

库存流水保存操作类型、变化数量、变更前后库存、单价、操作人和业务备注，可用于审计、追责、对账和库存恢复。只保存当前库存无法解释“库存为什么变成这个数”。

### 29. 账单状态应该如何设计？

**参考回答：**

项目中状态包括未支付、已支付、已退款。更完整的设计可以用枚举和明确的状态迁移：

```text
UNPAID -> PAID -> REFUNDED
UNPAID -> CANCELLED
```

支付接口应使用条件更新保证幂等，重复请求不能重复扣款；接入第三方支付后还需要支付单、外部流水号、异步回调验签和补单机制。

### 30. 如何防止重复生成挂号账单？

**参考回答：**

代码会先按预约和费用类型查询是否已有账单再插入，但单纯“先查再插”在并发下仍可能重复。更可靠的方案是在数据库建立唯一约束，例如 `(appointment_id, item_type)`，插入冲突后按幂等成功处理。

## 五、JWT、Redis 会话与安全题

### 31. 为什么项目同时使用 JWT 和 Redis 会话？

**参考回答：**

纯 JWT 是无状态的，服务端很难主动注销、踢人或立即撤销 Token。项目在 JWT 完成签名和过期校验后，还到 Redis 检查会话是否存在，因此可以实现主动登出、多端会话管理和账号级强制下线。

代价是每次认证增加一次 Redis 访问，系统不再是完全无状态。

### 32. JWT 中保存了哪些信息？

**参考回答：**

访问 Token 保存账号和角色，并带签发时间、过期时间和 subject；使用 HS256 签名。敏感个人信息和密码不应放入 JWT，因为 JWT 通常只是编码和签名，不是加密。

### 33. Refresh Token 流程应该注意什么？

**参考回答：**

Refresh Token 的有效期更长，只用于换取新的访问 Token。服务端必须校验：

- 签名和过期时间。
- Token 的 `type` 必须是 `refresh`。
- Token 是否被撤销、是否属于该账号和客户端。
- 是否采用刷新令牌轮换，旧 Token 使用后立即失效。

当前项目刷新逻辑只验证 Token 有效性并提取账号，没有显式校验 `type=refresh`，理论上访问 Token 也可能被拿去刷新，这是需要修复的安全点。

### 34. 为什么密码使用 BCrypt？

**参考回答：**

BCrypt 是带盐的慢哈希算法，同一密码每次生成的哈希不同，可降低彩虹表攻击效果；计算成本也能提高暴力破解代价。密码不能使用可逆加密或普通 MD5/SHA 直接存储。

### 35. 项目的权限校验如何完成？

**参考回答：**

JWT 拦截器验证 Token 和 Redis 会话后，将账号、角色和用户信息写入请求属性及 Session。业务 Service 再校验角色，例如只有 doctor 可以结束就诊，只有 pharmacist 可以审核和发药，患者只能操作自己的预约和报告。

**追问：还可以怎样改进？**

可引入 Spring Security，使用统一的认证上下文和方法级授权注解，避免每个 Service 重复从 Session 取角色。还应使用细粒度资源授权，不能只检查角色，还要检查数据是否属于当前用户或当前医生。

### 36. JWT 与旧 Session 拦截器同时存在有什么问题？

**参考回答：**

当前 JWT 拦截器验证后又向 HttpSession 写入用户信息，旧 Session 拦截器随后检查 Session，因此可以兼容旧代码，但会增加状态和认知复杂度。若两套白名单不一致，还可能出现认证行为差异。更好的方向是逐步统一到一种认证上下文。

### 37. 从 URL 查询参数读取 Token 有什么风险？

**参考回答：**

URL 可能被浏览器历史、代理日志、访问日志和 Referer 记录，导致 Token 泄露。应优先使用 Authorization Header；SSE 或下载场景若不方便设置 Header，可以使用短期一次性票据或安全 Cookie，而不是长期访问 Token。

### 38. 项目做了哪些 Web 安全处理？

**参考回答：**

系统设置了 `X-Content-Type-Options`、`X-Frame-Options`、CSP、HSTS、Referrer-Policy 和禁止敏感响应缓存等 Header；PDF 下载前会校验当前用户是否有权访问报告，并规范化路径，确保文件位于允许目录内，防止路径遍历。

## 六、AI、RAG 与 Kafka 题

### 39. AI 药品推荐的完整流程是什么？

**参考回答：**

1. 从数据库读取可用药品。
2. 将每种药品按摘要、功效、成分、副作用、禁忌和用法用量拆成多个字段级 chunk。
3. 分批调用 Embedding 模型并写入向量存储。
4. 用户输入症状后，同时执行向量检索和关键词检索。
5. 使用 RRF 融合两种结果，得到候选药品。
6. 把用户症状和候选药品上下文交给聊天模型。
7. 要求模型以 JSON 形式返回最多 3 种药品、理由、剂量和注意事项。

### 40. 为什么药品数据要按字段切分，而不是整条记录做一个向量？

**参考回答：**

整条药品记录可能很长，不同字段语义混杂。字段级切分能让“成分过敏”“某种禁忌”“某个症状对应功效”等查询更准确地命中相关片段；metadata 中保存药品 ID、名称和字段类型，召回后可以再按药品聚合。

### 41. 为什么同时使用向量检索和关键词检索？

**参考回答：**

向量检索擅长语义相似，例如“嗓子疼”和“咽喉疼痛”；关键词检索擅长精确药名、成分和专业术语。两者组合可以提高召回的稳定性，避免单一检索方式的偏差。

### 42. RRF 是什么，为什么适合混合检索？

**参考回答：**

RRF，即 Reciprocal Rank Fusion，根据候选项在每个检索列表中的名次计算融合分数：

```text
score(d) = Σ 1 / (K + rank_i(d))
```

它依赖排名而不是直接相加原始分数，因此不需要强行对齐向量相似度和关键词得分的不同量纲，适合快速融合多个召回通道。

### 43. 如何降低大模型幻觉风险？

**参考回答：**

- 只允许模型从检索到的数据库药品中选择。
- Prompt 强制结构化 JSON 输出。
- 返回药品后再按数据库记录校验。
- 明确最多推荐数量，并要求输出禁忌、副作用和免责声明。
- 医疗场景中不能让 AI 代替医生诊断，高风险症状应提示及时就医。
- 进一步可使用 JSON Schema、函数调用、敏感词规则和人工审核。

### 44. 为什么需要对 AI 检索做离线评测？

**参考回答：**

“感觉结果不错”不可量化。项目通过标注查询与相关药品集合，对纯向量、纯关键词、混合检索和混合加精排进行比较，指标包括 P@10、R@10、F1、NDCG、MRR、MAP 和延迟。

最近保存的评测报告中，关键词检索的 P@10 为 0.0667、R@10 为 0.6667，向量检索指标为 0。面试时不能把这组结果描述成“混合检索已经显著提升”，更诚实的结论是当前评测暴露出向量检索链路或评测数据仍需完善，例如检查向量库是否正确注入、标注集规模、药品 ID 映射和查询覆盖度。

### 45. P@K、R@K、NDCG 和 MRR 分别衡量什么？

**参考回答：**

- P@K：前 K 个结果中相关结果的比例，衡量准确性。
- R@K：所有相关结果中有多少被前 K 个结果召回，衡量覆盖率。
- NDCG：考虑相关结果所在位置，越相关的结果排得越靠前越好。
- MRR：第一个相关结果排名的倒数，衡量用户多快看到首个正确答案。

### 46. 向量索引持久化有什么好处和风险？

**参考回答：**

持久化后应用重启可以直接加载索引，避免每次启动都调用 Embedding API，降低启动时间和成本。风险是数据库药品更新后索引可能过期，需要保存索引版本或数据更新时间，并提供增量更新、重建和原子切换机制。

### 47. Kafka 在项目中承担什么职责？

**参考回答：**

Kafka 用来异步执行耗时 AI 任务。生产者提交任务并返回 taskId，消费者按任务类型调用 AI 药品、费用或报告服务，结果写入任务存储，前端轮询或查询结果。这样可以避免 HTTP 请求长时间阻塞，并对流量起到缓冲作用。

### 48. Kafka 消费如何保证不重复处理？

**参考回答：**

Kafka 通常只能做到至少一次投递，因此消费者必须幂等。可以：

- 使用 taskId 作为业务幂等键。
- 处理前查询任务状态，已完成则直接返回。
- 结果表为 taskId 建唯一约束。
- 数据库提交成功后再确认 offset。
- 失败时有限重试，超过次数进入死信队列。

### 49. Kafka 不可用时怎么办？

**参考回答：**

项目提供 Fallback 实现，可以降级为同步或本地处理。生产中还应加入超时、熔断、消息积压监控和告警。若任务已经接受但消息发送失败，必须明确返回失败或写入本地 Outbox，不能假装任务提交成功。

### 50. SSE 和普通 HTTP、WebSocket 有什么区别？

**参考回答：**

- 普通 HTTP 通常一次请求对应一次完整响应。
- SSE 基于 HTTP 长连接，服务端单向持续推送文本事件，适合报告生成进度。
- WebSocket 是全双工通信，适合双方频繁实时交互。

项目用 `SseEmitter` 推送报告生成步骤、进度、结果和错误。若规模扩大，需要独立线程池、超时与断连清理，避免每个连接无限占用资源。

## 七、缓存、前端与测试题

### 51. 项目缓存了哪些数据？

**参考回答：**

主要缓存药品、科室、医生、排班和费用等读多写少或查询频繁的数据。Spring Cache 负责统一注解，Redis 作为分布式缓存，使多实例共享缓存。

### 52. 如何处理缓存一致性？

**参考回答：**

查询使用 `@Cacheable`，新增、修改、预约和支付等写操作使用 `@CacheEvict` 清理对应缓存。当前不少地方采用 `allEntries=true`，实现简单但清理范围较大。进一步可以按实体 ID、科室 ID、医生 ID 或日期设计更细粒度 Key。

### 53. 如何防止缓存穿透、击穿和雪崩？

**参考回答：**

- 穿透：缓存空值、参数校验、布隆过滤器。
- 击穿：热点 Key 互斥重建、逻辑过期、后台刷新。
- 雪崩：TTL 加随机值、分批预热、多级缓存、Redis 高可用和限流降级。

### 54. 前端为什么使用 Pinia 和 Axios 拦截器？

**参考回答：**

Pinia 集中保存用户身份、Token 和预约状态，避免页面间重复传递。Axios 请求拦截器统一添加 Authorization Header，响应拦截器统一处理业务错误和 401，减少各页面重复代码。

### 55. 前后端如何实现角色路由控制？

**参考回答：**

登录后保存用户角色，Vue Router 守卫判断页面是否需要登录、当前角色是否有权限，并跳转到患者端、医生工作台、药师工作台或管理员控制台。但前端路由只能改善用户体验，真正的安全边界仍必须由后端鉴权。

### 56. 项目有哪些测试层次？

**参考回答：**

- JUnit/Mockito 单元测试：Service 分支、密码工具、正则和指标计算。
- Spring 集成测试：患者、预约和 Controller 接口。
- Redis 并发测试：锁互斥、过期、错误解锁和预约防超卖。
- 缓存性能测试：比较首次查询与缓存命中后的耗时。
- AI 检索评测：比较不同召回模式和排名指标。
- Selenium 端到端测试：登录、预约、费用、报告和药品查询。

仓库中约有 177 个 `@Test` 测试方法，但面试时应区分“写了多少测试”和“当前环境下全部通过”，只有实际执行后才能声称通过。

### 57. 单元测试和集成测试有什么区别？

**参考回答：**

单元测试隔离数据库和外部服务，通过 Mock 验证单个类的分支与交互，速度快；集成测试启动 Spring 上下文并连接真实或测试替代的基础设施，验证配置、事务、SQL 和组件协作。两者互补，不能只依赖其中一种。

### 58. 并发测试为什么不能只使用 Mock Redis？

**参考回答：**

Mock 只能验证调用逻辑，不能证明 Redis Lua 原子性、过期行为和多客户端竞争。分布式锁和库存扣减应至少使用真实 Redis 或 Testcontainers，在多线程甚至多进程环境下验证。

## 八、面试官最可能深挖的代码问题

### 59. 如果创建预约时号源递增成功，但插入预约失败，会发生什么？

**参考回答：**

可能出现号源被占用但没有预约记录。原因是数据库操作未必处于同一有效事务，尤其当前 `doCreateAppointment()` 存在同类内部调用导致事务代理失效的问题。应把号源更新、预约插入和账单插入放入一个真正生效的数据库事务；Redis 预扣则在数据库失败时补偿，并通过定时对账兜底。

### 60. 如果请求在 MySQL 更新成功后、Redis 回补或响应前崩溃怎么办？

**参考回答：**

单靠 try/catch 无法覆盖进程崩溃。需要持久化操作状态，通过 Outbox、任务表或领域事件记录待同步动作；后台消费者重试，并定时比较 MySQL 有效预约数和 Redis 库存，发现差异后修复。

### 61. 如何保证一个患者不能重复预约同一排班？

**参考回答：**

当前代码中的防重复查询被临时注释，不能依赖应用层先查。更可靠的方法是在数据库建立能够表达业务规则的唯一约束，或维护预约幂等键；取消记录是否参与唯一约束，需要根据数据库能力使用有效状态标记、单独占用表或事务内条件判断设计。

### 62. 为什么 `@CacheEvict` 和 `@Transactional` 的执行顺序值得关注？

**参考回答：**

如果事务最终回滚但缓存已经被清理，一般只是造成一次缓存未命中；如果先更新缓存后事务回滚，则可能产生脏缓存。常见策略是数据库提交成功后再删除缓存，必要时使用事务同步回调或消息通知。

### 63. 发药时多个药品应该怎样避免死锁？

**参考回答：**

并发事务如果以不同顺序锁定多个库存行，可能形成循环等待。应按药品 ID 或库存 ID 固定排序后依次锁定，缩短事务时间，并对死锁异常进行有限重试。

### 64. 医疗 AI 系统除了技术正确性，还要考虑什么？

**参考回答：**

- 隐私：个人健康信息最小化收集、脱敏、加密和访问审计。
- 安全：不能把 AI 建议直接当成处方，高风险场景需人工确认。
- 可解释性：展示依据和数据来源，而不是只给结论。
- 合规：保存模型版本、Prompt 版本和生成记录，支持追溯。
- 数据质量：过期、错误或冲突的药品信息会直接影响推荐。

### 65. 如果让你重构这个项目，你会先做什么？

**参考回答：**

优先级可以这样回答：

1. 修复预约事务自调用，让号源、预约和账单处于明确事务边界。
2. 恢复防重复预约并增加数据库幂等约束。
3. 将发药库存更新改成条件更新或行锁，保证并发安全。
4. 统一 JWT 认证上下文，删除双拦截器和业务层 Session 依赖。
5. 为 Redis/MySQL 双写增加对账与补偿任务。
6. 修复并扩大 AI 评测集，再决定向量、关键词和精排参数。
7. 将缓存失效从全量清理改为精确 Key。

## 九、场景设计题

### 66. 如果预约流量突然增长 100 倍，如何演进？

**参考回答：**

- 接入层限流、验证码和防刷。
- 排班数据和号源预热到 Redis。
- Lua 原子扣减，快速返回无库存请求。
- 成功预占后异步写入或排队处理，但必须提供明确的预约中状态。
- Kafka 削峰，消费者按排班 Key 有序处理。
- 数据库按条件更新兜底，建立唯一约束。
- 增加超时释放、补偿和对账任务。
- 监控成功率、锁等待、Redis 库存、数据库冲突率和消息积压。

### 67. 如何设计预约接口幂等？

**参考回答：**

客户端首次进入确认页时获取一次性幂等 Token，提交时服务端用 Redis `SETNX` 或数据库唯一键占用该 Token；相同 Token 的重复请求直接返回第一次结果。业务层再通过患者、排班和有效状态约束阻止重复预约。

### 68. 如何设计 AI 任务状态机？

**参考回答：**

```text
PENDING -> RUNNING -> SUCCESS
                   -> FAILED
                   -> TIMEOUT
PENDING/RUNNING -> CANCELLED
```

任务表保存 taskId、任务类型、请求摘要、状态、重试次数、结果、错误信息、创建和完成时间。消费者使用状态条件更新抢占任务，保证重复消费不会重复执行。

### 69. 如何监控这个系统？

**参考回答：**

- 接口：QPS、P95/P99、错误率、401/403 比例。
- 预约：成功率、号源冲突率、重复请求、Redis/MySQL 库存差异。
- 数据库：慢 SQL、连接池、锁等待、死锁。
- Redis：命中率、内存、热 Key、超时。
- Kafka：生产失败、消费延迟、积压、重试和死信。
- AI：调用耗时、Token 成本、解析失败、检索指标和人工反馈。
- 业务：预约到诊率、处方审核时长、低库存数量、支付成功率。

所有链路应携带 traceId，便于从前端请求追踪到数据库、Redis、Kafka 和 AI 调用。

### 70. 如何保护医疗数据？

**参考回答：**

- 传输使用 HTTPS，敏感字段加密存储或脱敏展示。
- 基于角色和资源归属做最小权限控制。
- 对查看病历、导出报告和修改处方进行审计。
- 日志中不输出身份证、完整手机号、Token 和病历正文。
- 文件上传校验类型、大小和内容，使用不可预测文件名。
- 数据备份加密，并制定保存与删除策略。
